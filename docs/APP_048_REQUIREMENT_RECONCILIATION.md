# APP 048 — Revised brief to operational requirements

A current agreed brief now has a reviewed requirement handoff. Preparing it reuses unchanged requirements by stable brief item ID, prepares replacement drafts for changed items, creates drafts for additions and lists removed commitments for explicit retirement or retention independently. It considers the latest earlier generated link for each item, so an agreed revision skipped before generation does not lose the operational baseline. Requirements created independently of the brief are outside this process.

Leadership reviews existing and proposed content, manual edits and linked design assets, assessments and saved proposals. Every applied decision requires acknowledgement. Manual edits, linked work, retained scope and independently retired lineage also require a review note. Notes accumulate in the internal handoff record. Retirement retains the existing requirement archive capability: a lead with that permission can retire; other authorized leaders can review replacements and retain removed work independently. Internal handoff notes are unavailable to external reviewers/clients through RPC or raw-table reads.

Activation and supersession occur in one transaction, with existing requirement RPCs. The old requirement stays active until its replacement is activated. Existing applicability, assessments and saved proposal evidence stay with the old requirement; the new requirement needs its own design assessment. Removed work is archived only after an explicit decision. If already archived independently, leadership can confirm that retirement; an independently superseded lineage can be retained without modifying its replacement. A retired proposed draft can be rebuilt from the agreed item, preserving the retired record and prior review notes.

A pending added item can be explicitly matched to a pending removed item when the item was recreated with another ID. Matching never guesses from the title. It can be undone until activation. The existing requirement remains in place throughout this review. Repeated preparation and concurrent activation do not create duplicates. Replacement activation/supersession cannot bypass the handoff through the ordinary requirement RPCs. Initial newly added drafts retain the existing review-and-activate route when they are unchanged from their prepared content and retain active project responsibility.

Every write rechecks active project leadership/capabilities, project/revision scope and current agreed state. Project/brief/requirement locks serialize the operation. Review tokens include live requirement records, scope and linked-work identities; stale reviews fail without partial activation. The UI resets acknowledgement when the reviewed token changes. A prepared pending handoff must finish before another brief revision starts. Existing accepted design baselines and evidence are not rewritten or automatically withdrawn.

The original `generate_brief_requirements` entry point now prepares this handoff. Historical views cannot generate or apply changes. The current page shows preparation/completion and pending counts, with a shortcut from the agreed status. Existing legacy generated links are adopted during preparation; earlier active requirements and manual changes are preserved for review.

Validation: `tests/access/brief-reconciliation.mjs` covers first-generation compatibility, reuse, atomic replacement, stale tokens, manual edits, explicit match/undo, independent requirements, archive capability, linked-work preservation, independently retired records/draft recovery, concurrent application, external/raw access denial and later revision continuity. `tests/access/brief-handoff-browser.mjs` covers the complete client-feedback/agreement/operational handoff journey, direct navigation, role controls and desktop/mobile. Existing project-brief API/browser tests exercise activation before starting another prepared revision.
