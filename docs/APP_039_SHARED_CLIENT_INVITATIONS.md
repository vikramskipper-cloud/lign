# APP 039 — Shared client activation invitations

Creating multiple projects with the same pending client previously collided with `invitations_active_key`. Team & access separately rejected pending invitations. Both entry points now use `invite_stakeholder`, preserving its workspace/project leadership checks and workspace-scoped external identity. Each project retains its own participant role, professional label and submission grant; conflicting roles within the same project are rejected atomically.

A valid pending invitation is reused without rotating its hash, resetting its expiry, creating another invitation or returning a fabricated token. The original single-use link activates the external identity and thus its explicitly assigned project participations. Wrong-account, expired, revoked and replayed claims fail. Revoked workspace identities cannot be restored by project leads or claimed through old links. Expired sent rows are marked expired before a fresh invitation is created; revoked invitation links remain invalid when a new invitation is issued.

Already-active, linked stakeholders are added directly to the requested project without another activation invitation. No workspace or organisation membership is created. Clients still see only assigned projects, and design-version sharing/privacy gates are unchanged. A shared advisory transaction lock per workspace/email serialises invite creation, reuse and claiming; project creation also uses the existing workspace lock on its legacy direct path.

RPC signatures remain compatible. `invite_stakeholder` and `invite_project_participant` return a token only for newly created invitations. A pending reuse returns the existing invitation ID and expiry with a null token. An already-active identity returns null invitation ID/token/expiry. `create_project_full` and its client-details wrapper expose a `state` of `created`, `pending` or `active` per external client. UI success states explain reuse or immediate access and offer copy-link controls only for actual new tokens. Reuse/active outcomes do not queue duplicate invitation email. Original plaintext links cannot be recovered from their hashes; a lost pending link must be explicitly revoked/replaced by authorised workspace leadership rather than silently rotated while adding another project.

Migration: `20261117020000_app_039_shared_client_invitations.sql`. It replaces three checked functions without changing tables, indexes, RLS or role grants. Claiming rechecks invitation state under lock before activation. Existing unique pending-invitation and identity constraints remain intact. Rollout ships the backward-compatible nullable-result UI through GitHub/Vercel before applying the migration.

Validation: `tests/access/shared-client-invitations.mjs` covers both project-creation RPCs, Team & access RPCs, unchanged link/expiry, case normalisation, identity deduplication, per-project roles, single-use exact-recipient acceptance, unassigned/other-workspace isolation, active clients, expired/revoked links, workspace revocation, concurrent invite/create/claim calls and rollback of invalid batches. The browser suite covers pending/active result messages, absence of invalid copy links and duplicate email-queue requests, repeated project creation, original-link acceptance, project sign-in and mobile layout. The design-version sharing regression verifies private drafts, exact-recipient shares and pending-invitation activation. All fixtures are local; hosted smoke is read-only.
